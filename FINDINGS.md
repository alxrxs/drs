# Findings: what Windows does for on-premises Hello key trust that the specifications do not say

Lab, 2026-11-10: domain `hellolab.test` (Windows Server 2025 DC, AD CS enterprise CA, AD FS on Server 2025), client Windows 11 Pro 26H2 (build 26300.9457, vTPM, Secure Boot, domain-joined), all on an isolated network. The reference enrolment was recorded against AD FS with mitmproxy (first as a WinHTTP/WinINet proxy, then transparently: DNS pointed the federation name at a reverse proxy holding an enterprise-CA certificate), plus the client's event logs, `dsregcmd`, AD FS's admin and debug logs, and LDIF dumps of the directory before and after. Every finding below was then confirmed by drs itself enrolling the same client with AD FS stopped and disabled. A second domain, `sambalab.test`, has a Samba DC alone (forky's 4.25.1 with the samba!4794 key-trust patches; no Windows DC, no AD CS, no AD FS), with a Windows 11 Enterprise LTSC 2024 client (24H2, 26100.1742). There, drs took the client through device join, Hello enrolment, PIN sign-in (online by PKINIT against the Samba KDC, and offline from cached credentials) and re-enrolment after `certutil -DeleteHelloContainer`. A second lab independently confirmed the core sequence on 25H2 (26200.9168) against a Windows Server 2025 DC; findings from it are marked (second lab).

**Decision point (phase 3): a server-side reimplementation is possible.** Nothing the client checks needs a Microsoft-signed artefact. Everything it validates is either ours to produce (tokens, certificates, the session-key blob) or standard (TLS, Kerberos, PKINIT).

## 1. The device-join token for a domain-joined PC

The client (`Dsreg/10.0`, as SYSTEM, from the `Automatic-Device-Join` task) gets it from **WS-Trust 2005 `windowstransport`**, authenticating as the **computer account with Negotiate (Kerberos)**:

1. `GET https://<enterpriseDrsName>/EnrollmentServer/contract?api-version=1.2` with `Accept: application/json` (the JSON form of MS-DVRD's discovery).
2. `GET https://<enterpriseDrsName>/adfs/services/trust/mex`, the WS-MEX document; the client takes the `windowstransport` address from it.
3. `POST .../adfs/services/trust/2005/windowstransport`, a WS-Trust 2005 `RequestSecurityToken`: `AppliesTo` = the DRS resource ID (`urn:ms-drs:<id>`), `KeyType` = `NoProofKey`, `TokenType` = `urn:ietf:params:oauth:token-type:jwt`, `Authorization: Negotiate <Kerberos>`.
4. The answer is an RSTR whose `BinarySecurityToken` is base64 of a JWT (RS256) with `aud` = the DRS resource, `upn` = `<computer>$@<domain>`, `primarysid` = the computer's SID, `accounttype` = `DJ`, `PermitDeviceRegistration` = `true`, and **`onpremobjectguid` = the computer object's objectGUID** (base64 of its mixed-endian bytes). That GUID becomes the device ID.

AD FS's Extended Protection (channel binding) breaks this through an intercepting proxy: the capture needed `ExtendedProtectionTokenCheck None`. drs does not implement channel binding.

## 2. The sequence Windows runs

| When | Request | Who |
|---|---|---|
| boot / task | contract → mex → windowstransport → `POST /EnrollmentServer/device/?api-version=1.0` | `Dsreg/10.0`, SYSTEM |
| user sign-in | `GET /adfs/.well-known/openid-configuration`, then `POST /adfs/oauth2/token` `grant_type=srv_challenge`, then `POST /adfs/oauth2/token` `grant_type=jwt-bearer` with a device-signed request (the **enterprise PRT**) | `Windows-AzureAD-Authentication-Provider/1.0` (CloudAP) |
| PIN set-up | `POST /adfs/oauth2/token` jwt-bearer **signed with the PRT session key**, `amr_values=ngcmfa`, resource = DRS → `interaction_required` | the web view's broker (EdgeHTML UA) |
| | `GET /adfs/oauth2/authorize?response_type=code&client_id=dd762716-544d-4aeb-a526-687b73838a22&redirect_uri=ms-appx-web://Microsoft.AAD.BrokerPlugin/dd762716-...&resource=urn:ms-drs:<id>&login_hint=<upn>&response_mode=form_post&amr_values=ngcmfa&add_account=multiple&windows_api_version=2.0.1` | `Microsoft.AAD.BrokerPlugin` web view |
| | the second factor, then a `form_post` of `code` to the `ms-appx-web://` redirect | |
| | `POST /adfs/oauth2/token` `grant_type=authorization_code` → the **ngcmfa access token** | web view |
| | `POST /EnrollmentServer/key/?api-version=1.0` `{"kngc": ...}` with that token | `Dsreg/10.0` |
| after | a PRT refresh (srv_challenge + session-signed request); `PUT /EnrollmentServer/device/<id>` (AD FS answers 400 too) | |
| every PIN or biometric sign-in | `srv_challenge`, then a device-signed jwt-bearer whose inner grant is **also** `jwt-bearer`: an `assertion` signed with the user's Hello key (MS-OAPXBC 3.2.5.1.2.1.2) → a new PRT | CloudAP |
| PRT renewal | a device-signed jwt-bearer with inner `grant_type=refresh_token` and the old PRT (second lab) | CloudAP |

- **Discovery `api-version`: 1.2.** The domain-joined client goes to the SCP's `enterpriseDrsName` host directly, not to `enterpriseregistration.<upn suffix>`, and it derives the `mex` path itself, so a replacement must serve AD FS's paths at that host.
- **The PRT is obtained at every interactive sign-in**, with the user's password relayed in a device-signed request (`client_id` `38aa3b87-a06d-4817-b275-7a316988d93b`, `scope` `openid aza ugs`, `grant_type` `password`).
- **The web view carries the PRT**, as `x-ms-RefreshTokenCredential` (an HS256 JWT signed with a key derived from the session key, `kdf_ver` 2), not a device-certificate header and not Kerberos. AD FS then challenges for Windows authentication, which the web view prompts for; drs sends it to Keycloak instead.
- **The web view bypasses the WinHTTP and machine-wide WinINet proxies**, and its broker connects to the federation host directly.
- The client also probes `POST /common/oauth2/token` (Entra's path) and copes with a 404.
- **The Hello assertion at sign-in**: header `alg` RS256, `use` `ngc`, `kid` = standard base64 of SHA-256 over the key material (the key's KeyID entry); body `iss` = the UPN, `aud` = `HTTPS://<HOST>/ADFS/LS/` (upper-cased), `request_nonce` = the outer one, `scope`, and `iat`/`exp` **as strings**. Without an answer to it the user signs in (Kerberos does not need it) but holds no PRT afterwards. It is also what recovers a client whose PRT the server can no longer open (a state-key rotation): its next PIN sign-in gets a fresh one.
- Also sent and safely refused with 400: a device-signed `grant_type=device_token` (client `8ed735f8-…`, resource `events.data.microsoft.com`) (second lab).
- `dsregcmd /status` run as SYSTEM always shows `EnterprisePrt : NO`; the PRT is the user's, visible only in their session.
- **How AD FS answers the rest** (a second lab's recording of Server 2025 AD FS; drs answers the same): a session-signed request for the DRS resource is always `401 interaction_required` (MSIS9700); one from a client AD FS does not know (Windows' first-party `82864fa0-…`, `ecd6b820-…`, `e2ef5054-…`, `ab9b8c07-…`, `bed12bc0-…`) is `400 invalid_client` (MSIS9607); a PRT renewal signed with the session key (client `38aa3b87-…`, inner `refresh_token`) returns a whole new PRT as plain JSON, its id_token keeping the original `auth_time` and echoing the request nonce; `device_token` is `400 invalid_request` (MSIS9679). The id_tokens of the Hello-key grant and of the code exchange carry `mfa_auth_time`.
- **Lock and unlock** is `srv_challenge` plus the Hello-key grant, a new PRT each time; **PIN change** makes no server call at all (second lab).
- **The lock screen's "I forgot my PIN" does not reach an on-premises DRS** (24H2): it first requires Windows' internet check (NCSI), then verifies the password with a password-grant PRT, then hands the new set-up to Entra's PIN reset service (realm discovery at `login.microsoftonline.com` fails) and falls back to the PIN prompt. On-premises PIN reset is the in-session one (Settings > Sign-in options > PIN > "I forgot my PIN"): the Hello set-up sequence again — session-signed DRS request → 401 → `/authorize` → second factor → code → `ngcmfa` token → `POST /key`, a new key (AD FS: second lab, 25H2; drs: 24H2, Keycloak in place of Windows authentication). Windows never deletes the old key: AD FS leaves one stale `msDS-KeyCredentialLink` value per reset, while drs replaces the user's earlier NGC key bound to the same device in the same write. On 25H2 the lock-screen reset runs this same sequence (second lab); on our 24H2 it handed off to Entra. Deleting the container (`certutil -DeleteHelloContainer`) and provisioning at the next sign-in does the same.
- **Cut-over without re-join** (second lab): with AD FS stopped and its SPN on drs's account, drs accepted the AD FS-issued device certificate and the AD FS-written NGC key — a PRT by the Hello-key grant at unlock and at sign-in. **Clients keep their cached `HTTP/<host>` service ticket** for up to its 10-hour life after the SPN moves, so `windowstransport` fails (Kerberos checksum, 401) until it expires or `klist -li 0x3e7 purge`; sign-in, PRTs and PIN are unaffected, only a join or device re-check. Our lab hit the same as an RC4 ticket after the move.
- **Only the broker gets a PRT on the device-signed path.** After an error Windows retries Hello set-up as a device-signed request from the DRS client (`dd762716-…`, inner `refresh_token`); AD FS answers 401 MSIS9700 (back to `/authorize`), and a PRT given to it leaves the client with a stale one (0x801C044D) until the next password sign-in (second lab).

## 3. What the client validates in our responses

- **The PRT session key, for a TPM-held transport key, is a TPM 2.0 duplication blob, not RSA-OAEP.** `session_key_jwe`'s "encrypted key" is `TPM2B_ENCRYPTED_SECRET (256) | TPM2B_PRIVATE (108) | TPM2B_PUBLIC (48)`: the session key as a KEYEDHASH (HMAC-SHA256) object outer-wrapped to the transport key (seed RSA-OAEP-SHA256 with label `DUPLICATE\0`, KDFa `STORAGE`/`INTEGRITY`, AES-128-CFB), which Windows imports with `NgcImportSymmetricPopKey`. A plain OAEP ciphertext fails with "Object was not found", the logon reports 0xC0090011, and Hello never launches ("User has logged on with Microsoft Entra credentials: No"). `drs/tpm.py`; `tests/test_tpm.py` performs TPM2_Import's checks.
- **The transport key is a Platform Crypto Provider blob** (`PCPM`, its TPM2B_PUBLIC holding an RSA-2048 storage key, SHA-256, AES-128-CFB), not the `RSA1` BCRYPT blob ROADtools and MS-DVRJ suggest.
- **TLS:** the web view refuses a server certificate from a CA that is only added to the machine's trusted roots (mitmproxy's); one from the AD-published enterprise CA works. Never request a client certificate: the registration client aborts any handshake that does (WinHTTP 0x80072f0c).
- The `id_token` claims read: `upn` (the user), `unique_name`, `sid`, `nonce`; drs's minimal set is accepted. Tokens are RS256 JWS; the token endpoint's encrypted responses are `dir`/`A256GCM`. **How Windows names the Hello work account** (Start-menu tile, account flyout; second lab, 25H2, broker account files `…\AAD.BrokerPlugin…\AC\TokenBroker\Accounts\*.tbacct` read after each step). The account is keyed on the user's SID (`u:<SID>.enterprise`). At the first sign-in Windows creates it with DisplayName = the PRT id_token's `sub` (any `name` there is ignored). Hello set-up then rewrites it from the set-up code exchange's id_token: DisplayName/FirstName/LastName = `name`/`given_name`/`family_name`, removed when absent. Nothing rewrites it afterwards. The Start menu reads it at session start, so the corrected name appears from the next sign-in. AD FS sends name claims in that id_token only with an issuance rule for them *and* `allatclaims` granted to the broker client `dd762716-…` on the DRS resource; by default the name ends up blank. On a production AD FS (Server 2022, FBL 4, the default DRS rules) that combination **breaks Hello set-up**: the id_token's `unique_name` then reaches the client in a form it cannot read, and set-up and PIN reset fail with `0xCAA60009` "Could not convert JSON type. (unique_name)" (AAD/Operational 1098). So on such a farm the name stays blank, which is where the Start menu's account flyout and Settings' header show only the UPN while the sign-in screen and Settings > Your info, which read AD, show the display name. drs sends `sub` = the AD display name (the UPN when there is none; never read back as an identity) and, in every id_token, `name`/`given_name`/`family_name` from AD's `displayName`/`givenName`/`sn`, read at the code exchange. A renamed user keeps the old name until their `.tbacct` files are deleted while they are signed out, or the Hello set-up runs again.
- **TLS for the web view**: a certificate from a CA in the client's Root store is enough (the Samba domain's CA, and Keycloak's from another forest's CA, both only imported). The earlier mitmproxy refusal was not about AD publication.
- **The KDC certificate, without AD CS** (a Samba DC): Windows validates it before accepting a PKINIT reply, and needs (1) its issuer in the client's **enterprise** NTAuth store, which autoenrolment fills from `CN=NTAuthCertificates,CN=Public Key Services,…` (`certutil -addstore NTAuth` fills a different store; event 9 "not trusted by the policy provider"), and (2) a revocation check it can make: an `ldap:///` CDP to a CRL published under `CN=CDP` (event 9 "unable to check revocation"). AD CS provides both; a Samba-only domain must publish them itself.
- **The public-key SID differs by KDC**: a Windows DC asserts `S-1-18-4` (Key trust identity) in the user's token, the Samba KDC `S-1-18-3` (Fresh public key identity), both beside `S-1-18-1`.
- The device certificate as AD FS issues it: subject `CN=<device id>`; issuer `MS-Organization-Access`; BasicConstraints and EKU (clientAuth) critical, no key usage; extensions `1.2.840.113556.1.5.284.1` (invocationId), `.2` (device id), `.3` (here also the computer's GUID), `.4` (domain GUID), and **`.7` = the string "1"**, which MS-DVRJ does not list.
- The error bodies the client understands: OAuth's `{"error","error_description"}` on `/adfs/oauth2/*`; MS-DVRJ's `ErrorDetails` on `/EnrollmentServer/*`.

## 4. What `dsregcmd /status` must show before Hello provisions

`NgcPrerequisiteCheck` needs `IsDeviceJoined : YES` (from the device join above) and, at the user's sign-in, an enterprise PRT ("User has logged on with Microsoft Entra credentials: Yes" in event 360). Before the device join the check reads `WillNotProvision`. Our responses drive both: the join response and the PRT response.

## 5. The SCP

`CN=62a0ff2e-97b9-4513-943f-0d221bd30080,CN=Device Registration Configuration,CN=Services,<configuration>` with **one keyword: `enterpriseDrsName:<federation host>`**. `Initialize-ADDeviceRegistration` does not create it; without it `dsregcmd` reports `AD Configuration Test : FAIL [0x80070002]` and the join stops in the discover phase. DNS alone (`enterpriseregistration.<suffix>`) is not used by a domain-joined client. **Migration from Entra:** an SCP still naming an Entra tenant (`azureADName`/`azureADId` keywords) sends the client to Entra; replace the keywords with `enterpriseDrsName` only. `CN=RegisteredDevices` must be an `msDS-DeviceContainer`.

## 6. Re-provisioning

`dsregcmd /leave` removes the client's registration but not the device object, and calls no DELETE; the next `Automatic-Device-Join` re-registers the same device ID (drs updates the object in place). After `certutil -DeleteHelloContainer` the next password sign-in runs Hello set-up again, second factor included, and adds a second key; the first stays in `msDS-KeyCredentialLink`, unusable since its private key went with the container (AD FS behaves the same). A second user on the same PC enrols independently (second lab). Offline, a PIN sign-in is a cached logon (4624 type 11). With Credential Guard running (VBS, `LsaIso`), the PIN sign-in, its PKINIT TGT and the PRT work unchanged (24H2 against the Samba KDC). A device registered by AD FS keeps working with drs: drs finds it by `altSecurityIdentities`, whichever issuer signed its certificate. Moving a PC from cloud Kerberos trust: `dsregcmd /leave`, `certutil -DeleteHelloContainer` as the user, sign out and in; still to be run on a cloud-trust PC.

## 7. Stability across Windows updates

The same sequence works on 26H2 (26300.9457), 25H2 (26200.9168, second lab) and 24H2 (26100.1742). A run across a cumulative update is a second lab's, in progress. MS-OAPXBC's CVE-2023-35348 note (the server SHOULD check a user-JWT's `request_nonce` when its `kid` differs from the device's) concerns Hello sign-in to the token endpoint, which drs does not serve.

## Directory

- The user's NGC key as AD FS (Server 2025) writes it: version 0x200, KeyID, KeyHash, KeyMaterial (`RSA1` from `kngc`), KeyUsage NGC, KeySource AD, **DeviceId present**, **CustomKeyInformation flags 0** (MS-KPP says 0x02), the two timestamps. An older AD FS farm wrote keys with no DeviceId.
- The device's `altSecurityIdentities`: `X509:<SHA1-TP-PUBKEY><thumbprint><base64 SHA-256 of the PKCS#1 RSAPublicKey>`: **no `+`**, and not over the whole SubjectPublicKeyInfo, unlike MS-DVRJ 2.3.3.
- AD FS also sets `msDS-IsManaged = FALSE` on the device.
- **Samba refuses a DN-Binary `msDS-KeyCredentialLink` naming the object being created** ("Unable to find GUID for DN"); Windows accepts it in the add. A new device's key goes in a second write.
- The KDC reads only KeyUsage and KeyMaterial: CustomKeyInformation flags 0 and 2 both sign in (second lab).
- Without the schema, ldap3 sends Python booleans as `True` (AD wants `TRUE`) and returns GUIDs and SIDs as raw bytes.
- AD FS needs its service account in **Key Admins**; drs does with one ACE per OU (`WriteProperty msDS-KeyCredentialLink`, inherited to users) and two on `RegisteredDevices`.

## Capture limitations

- `windowstransport` through an interceptor needs AD FS's Extended Protection off.
- AD FS's certificate authentication runs on port 49443 with a client certificate, so it was relayed, not read.
- The registration client's JSON bodies end with a NUL byte.
